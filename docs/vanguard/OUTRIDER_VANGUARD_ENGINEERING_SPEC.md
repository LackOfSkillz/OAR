# Outrider Vanguard — Engineering specification v1.0

Date: 2026-11-26 | Status: proposed; owner authorization required | Program: VG | Target: WoW Forever, all nine classes, all supported roles, party and raid sizes verified per instance. Repository: LackOfSkillz/OAR. Inspected development baseline: `9a2fa615f368c91394b006987905afc863d7854f`; re-pin current approved baseline before implementation. This is a separate engineering program, not permission to merge, release, or supersede existing acceptance gates.

## 1. Mission and product promise
One Outrider installation should provide a useful pre-instance group assessment, even when every other member has no addon. Identify what is known, what is missing, which encounters are risky, and what the player can do to improve readiness. Combine native roster and permitted inspection evidence, role-specific models, encounter requirements, optional consent-based enrichment, historical outcomes and Nexus planning. A readiness index is not a success probability. SuccessForecast is gated until real, representative evidence establishes calibration. All basic features operate offline without Command Center, internet, AI, or peer installations. No mandatory accounts.

### Functional tiers
- T0 roster-only: class/level/role/subgroup where readable, manual encounter selection, potential utility, unknowns, access/preparation checklist for self; no remote equipment assumptions.
- T1 native inspection: user-started sequential scan of eligible roster members, verified equipment/talents where accessible; role-specific assessments, boss matrix, hypothetical roster optimization; no requirement to install peers.
- T2 consent sharing: optional Fellowship extensions for personally confirmed/observed preparedness and history; revocation, freshness, scope, explicit field preview.
- T3 optional desktop: post-session analytics, deeper simulations, calibrated forecast training and validation, consent-filtered export/import; separate Command Center gate. No dependency on T3.

## 4. Non-negotiable policy and data integrity
D18 advice-only and `docs/FOREVER_CONSTRAINTS.md` govern. No gameplay automation, protected action invocation, programmatic invitations, roster changes, combat control, input synthesis, client memory access, screen capture, network transport from addon to desktop, restricted combat-log registration or processing, secret-value arithmetic or comparisons, or attempt to circumvent restrictions. No background external live-game file polling. Use Compat; test secrecy before indexing, comparison, conversion, string formatting or storage. Never probe forbidden events by registering them. Use only permitted, verified native APIs; out-of-combat scanning only. Pause/cancel on combat, manual Inspect, roster churn, feature disable, zoning or logout; clean up only inspect state owned by Vanguard. Do not block ordinary game inspection or other addons. No public player rankings or automated chat shaming. User clicks to view/copy any report; reports default to aggregate, not names. No external upload, remote scraping or cloud AI by default.

Owner data-preservation override remains binding: never delete/overwrite gathered project datasets, original observations or attribution; audit and report questionable provenance, logically restrict use/distribution if necessary, preserve originals. Version, archive, validate and fail closed on migration errors. No data loss through limits, recovery, reset, export or rollback. Distinguish intentionally transient third-party inspection cache from permanent project knowledge: do not persist identifiable non-consenting peers' gear, names, GUIDs or talent snapshots. This is data minimization at collection design, not retroactive deletion of existing data. Store anonymized run-level composition features and outcomes, not member-linked histories; optional identified records require separate explicit consent and owner-approved privacy lifecycle. Consent withdrawal invalidates peer display/use promptly; legally required or privacy deletion uses separate documented authorization per owner directive. Never retain rejected new malicious packets. Backups and exports must honor scope and consent; do not put personal files or identifiable fixtures into Git.

## 5. Architecture and boundaries
Proposed namespace/module grouping (adapt to existing dependency conventions): Vanguard orchestrator, Roster/InspectBroker, ProfileNormalizer, CapabilityRegistry, EncounterCatalog, RoleAssessment, Coverage/Readiness, PreparationPlan, WhatIfOptimizer, GroupHistory, Forecast, UI adapter. Use pure calculation modules separate from API/event adapters. Register modules in existing TOC/dependency gates. State flow: native roster -> scoped observations -> normalized profile -> role and utility model -> encounter requirements -> readiness matrix -> Nexus opportunities -> user decision -> permitted outcomes -> immutable history -> calibrated model (if eligible). Evidence and revision identifiers attach to every derived result. Dependency graph must have no circular requires; feature default off until live verification, then owner-controlled rollout. No polling every frame. Feature disabled means no scan timers or event subscriptions except shared framework necessities. Avoid parallel duplicate native inspect consumers within Outrider.

## 6. Capability validation and native scan protocol
Build a capability matrix for exact Forever build and locale. Candidate APIs (NOT guarantees): UnitExists, UnitIsPlayer, UnitGUID, UnitName/UnitFullName, UnitClass, UnitLevel, UnitGroupRolesAssigned, GetNumGroupMembers, GetRaidRosterInfo, IsInRaid, CanInspect, NotifyInspect, INSPECT_READY, ClearInspectPlayer, GetInventoryItemLink, GetItemInfo/C_Item and modern/classic inspected talent interfaces, supported ready-check events, ENCOUNTER_START/END, instance IDs and permitted money/time events. Compare native Inspect UI and addon reads on real client, including one Outrider + four non-users and raid roster, range/offline/dead/zone/secret cases. Record exact signatures, safe context, build, success/error, sample redacted payload and fallback. No blind trial of forbidden APIs. If inspection cannot be safely automated, support individual explicit inspections or roster-only mode and disclose limitation.

InspectBroker state machine: idle -> queued -> request -> waiting -> collecting item metadata -> complete/partial/timeout -> next; canceled terminal on context change. One in-flight request; initial proposed interval >=2 seconds, timeout 8 seconds, at most one retry with backoff, bounded queue <= verified raid cap, total scan deadline 180 seconds (tune from client measurements, respect native throttles). No automatic repeated scans; explicit Refresh and optional per-member refresh. Check `CanInspect` and out-of-combat before request and reads; check native Inspect window/conflict and defer rather than taking over. Correlate `INSPECT_READY` with expected GUID, current roster epoch, request generation and token; ignore mismatches/late events, handle missing GUID safely. Native events may lack request IDs: do not re-use ambiguous requests; validate identity and freshness at collection. Inspect item links only when permitted; deferred item metadata resolution bound to immutable profile revision. Slot states distinguish empty, unreadable, pending, unavailable, known. Missing role: self/user confirm; infer only as tentative from verified talent/gear, never overwrite explicit assignment. Group roster keys use GUID when safely readable, canonical realm identity fallback, never merge ambiguous same names. Clear current-view cache on roster departure; no permanent raw peer cache. TTL suggested 5 minutes for inspection, stale explicit and revalidation on roster/role/gear changes where supported. No stale score presented as current; display scan progress and cancel.

## 7. Data contracts
All persisted own/anonymized records versioned, exact build/ruleset, content source, observed timestamp, derived timestamp, expiry where applicable, scope, revision and evidence IDs. Strings bounded; arrays bounded; reject unknown incompatible version; finite numbers only; no arbitrary Lua or code in imports. No external callback carried in a record. Proposed contract fields:
- `Observation {id, kind, value, unit, source:native|self|peer|manual|catalog|model, status:known|unknown|stale|conflicting|unsupported, observedAt?, expiresAt?, build, scope, evidenceIds[]}`. Unknown not 0. Manual confirmations labeled; derived values never overwrite observations.
- `RosterSnapshot {generation, instanceContext?, build, faction?, members:[{ephemeralKey, class?, level?, role?, roleSource, subgroup?, connected?, availability}]}`. Ephemeral member identifiers only in current roster cache.
- `MemberProfile {rosterGeneration, ephemeralKey, profileRevision, slots:[{slotId,state,itemId?,enchantId?,stats?,evidence}], talents?, roleCandidates[], stats:{statKey:Observation}, capabilities:[{capabilityId,state:verified|potential|absent_verified|unknown, scope, evidenceIds}], coverage}`. Separate modeled stats and actual visible stats. No inferred absence from missing API.
- `EncounterDefinition {instanceId, encounterId, difficulty, buildRange, sizeRange, accessGraphId?, requirements:[{id,category,weight,critical,unit,target?,rule,scope,sourceIds,verification}], availability:verified|reference|unknown, version}`. Raid unlocks, names, requirements and roster sizes not hardcoded from Classic; versioned facts and manual templates separate. Do not invent thresholds for unverified raids. Catalog source/attribution retained.
- `Assessment {id, rosterGeneration, profileRevisions, catalogVersion, contextRevision, scoreRange?, scoreKnown?, coverage, gateStatus, risks[], assumptions[], unknowns[], evidenceIds[], expiresAt}`. Display confidence based on measured coverage/quality, not a success rate.
- `PrepAction {id, requirementId, targetScope, expectedImprovementRange?, copperCost?, seconds?, prerequisites[], confidence, evidenceIds, permittedIntent, contextRevision}`. Nexus validates current state before navigation/panel actions; no action on another player.
- `RunRecord {runId, sessionId, instanceId, difficulty, build, startedAt, endedAt?, outcome:completed|incomplete|abandoned|unknown, censorReason?, aggregateRosterFeatures, snapshotCoverage, assessmentId?, encounterAttempts[], sourceIds, revision}`. Aggregate features only for nonconsenting peers; no individual identifiers persisted. `Attempt {id, encounterId, start?, end?, result:kill|wipe|unknown, evidence, contextRevision}`. Record coverage and roster changes; never infer wipe from disconnect alone.
- `Forecast {modelVersion, targetDefinition, horizon, cohort, estimate?, interval?, trainingCount, validationCount, calibrationMetrics, dataCoverage, abstainReason?, evidenceIds}`. No model without validated cohort and evidence.

## 8. Feature requirements
### GroupScan and RoleScore
Native roster overview, inspect queue, individual drilldown, gear slot details, enchant status, missing/unknown distinction, role-specific comparison, estimated stats and source labels. All nine classes and documented roles; hybrid and alternative builds supported. Level and instance difficulty normalize targets; do not use a single gear score to determine skill. Model tank armor/health/mitigation/avoidance/resistance and threat potential only where formula verified; healer pool/regen/bonus healing and endurance; DPS weapon/stat/talent potential by verified mechanics. Unsupported procs, resource systems and spell mechanics stay unknown. No fabricated health, DPS or HPS. Forge estimates reused only when model scope is adequate, label uncertainty and unsupported inputs. Empty confirmed slots are not same as unavailable slots. Peer not using Outrider is not a negative score factor.
### CompositionIQ and EncounterIQ
Evaluate role coverage, class ability potential, verified talents, interrupts, dispels by type, crowd control, resurrection/recovery, buffs/debuffs, tank/off-tank, healer coverage, faction-specific alternatives, party vs raid scope, stacking/exclusivity and encounter-specific requirements. Potential ability not necessarily trained, equipped, usable or executed. Never equate class count with demonstrated performance. Display boss-by-boss required/recommended/unknown checks and source trace, access/attunement dependencies, quests, loot, map entrance, current unlock status, repair, bags, carried consumables, class reagents, enchants and appropriate duration-based stock. Only self or opt-in confirmation for private inventory; bank stock is not carried. Access unknown not denied. Custom profiles and requirements are user assumptions, clearly marked. Distinguish encounter prerequisite from optimization preference. Never extrapolate unverified Classic raid mechanics to Forever silently.
### Readiness math (initial design, tune only with evidence)
For each applicable requirement j, weight w_j > 0 and fulfillment f_j in [0,1] based on verified target and rules. Unknown requirement result has interval [0,1], not failure. Verified or bounded estimates have [l_j,u_j]. Score range = 100 * sum(w_j*l_j)/sum(w_j) to 100 * sum(w_j*u_j)/sum(w_j). Known-only index = 100 * sum(w_j*f_j)/sum(known w_j), labeled partial and suppressed when evidence insufficient. Weighted coverage = known applicable weight / total applicable weight. Proposed threshold 0.8 for displaying a group point index; initial threshold is product policy, not empirical validation. Prefer range when incomplete, suppress numbers if requirements themselves lack verified targets. Critical checks separate: confirmed missing mandatory access/required role -> blocking issue; unknown critical -> not established; all known passed -> prerequisites observed, not guaranteed success. Low confidence never becomes a definitive negative. Maintain evidence coverage per role, boss and entire group; no average can conceal a missing critical mechanic. Score monotonic for an improvement to fixed requirement set, deterministic for identical inputs; use explicit cap and unit tests. Avoid double-counting correlated gear stats, cap duplicate utility benefits. Group readiness and encounter readiness are distinct; risk tags explanatory, not a probability.
### PreparationPlan / Nexus integration
Rank actions by criticality, marginal readiness gain, evidence quality, cost/time and player goals; dependency-aware (e.g., upgrade before enchant), alternatives, gold reserve, time budget, AH price known/unknown, crafting and owned materials, dungeon rewards, travel and access prerequisites. Compare practical affordable alternatives with aspirational BiS, not insist on one loadout. Add personal action plan using existing Nexus opportunity contract and validator; external members receive only suggested preparation text, never automated messages or orders. Group report copy preview with aggregate default; manual selection and permission. WhatNow and Radar must not duplicate contradictory recommendations. Recalculate context on roster/role/catalog/inspection/goal changes or expiry. Non-Nexus users still see checklist.
### RaidOptimizer
Hypothetical roster editor: swap/assign roles, add candidate class/spec or opt-in profile, move hypothetical subgroups, lock assignments, prioritize capability coverage, fairness and access; explain constraints and score deltas. No actual roster changes or invites. Bounded deterministic search, objective constraints and unknowns; compare baseline vs candidate, no claim of guaranteed improvement. Handle verified 5/10/20/40 or other sizes from catalog; do not assume raids all 40. Provide multiple feasible options and no-solution reason. Use subgroup-specific buffs and nonstacking rules. Unknown spec does not invent spells. Can compare proposed encounter-specific plans and estimated time ranges only with valid history.
### GroupHistory / SuccessForecast
Use permitted encounter/instance events, user-confirmed outcomes and existing history; no combat-log registration. Define instance completion per verified objectives; boss kill is not automatically full clear. Capture failed/abandoned/unknown/censored runs as distinct; record denominator and observation completeness, roster change, difficulty and build. Avoid per-member blame or skill ranking. Deduplicate across reload/rejoin; time-source handling and stable run identity. Aggregate history scoped by character/account as appropriate. Use immutable event/version records and archived history queries; do not discard originals. Record predictions before outcomes for evaluation, no post-outcome leakage. Initial historical descriptive rates: successes/eligible known outcomes with Wilson interval and sample count; show excluded/censored cases. Never present this as a personalized probability without validation. Candidate statistical model offline: regularized logistic or transparent hierarchical model on aggregate features, encounter/build/difficulty, no names. Chronological split, group by run and character/account where applicable; avoid leakage between attempts in same run. Baseline prevalence and simple role/level model comparison; report Brier score, calibration/reliability, sample sizes per bin, discrimination where useful, coverage/abstention, uncertainty and subgroup drift. Suggested initial release floors (must be reviewed and justified, not sufficient alone): >=200 independent labeled runs per applicable target cohort, >=50 held-out runs and >=10 outcomes in each class on holdout; reject sparse or skewed cohorts, domain shift, leakage or inadequate calibration. Establish target/threshold pre-registration before evaluating; require Brier no worse than prevalence baseline and positive calibration evidence with intervals; independent reviewer approves model. No multiply boss probabilities assuming independence; full-clear prediction trained/evaluated as separate target or abstain. Forecast target explicitly first attempt, eventual boss kill or full clear within stated time horizon; separate models. No percentages if evidence inadequate, missing critical inputs, build drift or model approval absent. Completion-time quantiles use comparable complete runs, disclose selection bias; do not imply time guarantee. Offline addon uses only approved lightweight model coefficients/data; no mandatory external AI. Desktop model development is separately gated. Never use LLM for numerical forecasts.
### UX and accessibility
Single Vanguard tab/section linked from Dungeon Journal and Fellowship. Views: Overview, Group Scan, Boss Matrix, Prep Checklist, What-if, Run History, Evidence. Compact 5-player and virtualized 40-player views, filters by subgroup/role/status, sort by actionable requirement not humiliating player ranking. Color + text/icon; scalable layouts, keyboard focus, tooltips, localization keys, demo fixtures marked sample. Show coverage, last updated, unknown reasons, disabled/unsupported features, progress/cancel and manual overrides. No UI mutation of protected frames in combat. Avoid constant warnings. Settings per character/profile; no destructive reset. Optional share shows exact fields, recipient scope, expiry and revoke controls.

## 9. Security, performance and testing
Threat model: spoofed sender, malformed or oversized packets, stale roster, late inspect results, GUID mismatch, secret data, malicious imports, timer leaks, unbounded histories, corrupted SavedVariables, consent revocation, cross-character scope, public disclosure, unsafe AI output. Reuse Comm rate/size limits; validate roster/channel/identity; revocation bypass ordinary update throttles only after identity validation; generation/sequence and expiry prevent stale updates reviving revoked state. No new PII to diagnostics, telemetry or Git. Fuzz packet/import boundaries and use bounded queues. Owner directive applies to previously persisted own data; do not preserve hostile new input. Data migration pre/post manifest with canonical contents, hashes and field/record equality, restore test; backup retained, atomic write or nondestructive recovery. Use same existing test pipeline and static checks.

Initial performance budgets, provisional until measured: no scan in combat; one timer/broker, bounded request count, no repeated scans, at most 2 ms typical CPU slice and 4 ms maximum target on reference client outside combat, p95 assessment <100 ms off-game for 40 profiles, incremental processing, <=5 MB transient cache target excluding existing packs, no UI row/frame growth per refresh, cancellation <1 event turn; define measured hardware/build and report worst-case rather than average only. Defer nonessential recomputation. Benchmark 5/40 members, missing items, 200 repeated roster churns, 100 canceled scans, 1000 history records and archive-scale history. No full unbounded history scan on a frame; use bounded queries, cached indexes and desktop deeper analysis. No silent truncation of permanent knowledge. Measure frame spikes, memory, timer and frame counts in real client.

Test layers: pure Lua math/property tests; native API mock and secret sentinel tests; integration tests actual producers->Vanguard->Nexus, Fellowship and AfterAction; malicious/negative tests; performance fixtures; migration and full data-content verification; cross-language fixtures if desktop; live protocol below. Do not claim pass for skipped cases. Require clean checkout full suite, exact-SHA CI or explicitly approved alternate independent reproducible run (CI billing blocker not automatic waiver), no new quality/dependency/security issues, evidence of negative tests failing old code where applicable. No test count target as substitute for coverage.
